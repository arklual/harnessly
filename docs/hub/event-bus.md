# Шина триггеров хаба (эпик HRN-1725)

Всё, что «случилось» у человека — письмо, сообщение в Телеграме, назначенная задача, упавшая сборка, готовая генерация в
сервисе через MCP, закончившийся чат агента, — попадает в хаб одним конвертом, ложится в один журнал и уходит каждому,
кто на это подписан. Дайджест, автоматизации, уведомления, виджеты в чате, задачи по триггеру и приложения через SDK —
равноправные подписчики. Новый подписчик не трогает источники, новый источник не трогает подписчиков.

Шина — часть открытого хаба. Закрытые сервисы (например, «Входящие») — такие же внешние подписчики через публичный API.

## Как было

Пять несвязанных путей: правила на машине, автоматизации хаба (`/hook`, `automations.event`, расписание, ожидание),
`/api/ingest` «Входящих» (только почта, календарь, ТГ), собственные сборщики «Входящих» (YouTrack, GitLab, GitHub) и
регулярные задачи. Трекеры, вики и сервисы через MCP событий не дают. Журнала нет: что сработало и почему — не видно.

## Устройство

```
источники ─► адаптер ─► журнал ─► обогащение ─► подписки ─► потребители
(коннектор, вебхук,     (Event v1,  (дедуп,       (фильтр,      (правила, дайджест,
 подписка MCP, рецепт    seq)        склейка,      курсор,       уведомления, виджет,
 опроса, harnessly, SDK)             thread)       доставка)     задачи, SDK, наружу)
```

### Event v1 — сырой конверт

Это `connectors.Event` (docs/connectors.md), поднятый на уровень хаба, плюс то, что знает только хаб.

| Поле | Что | Пример |
| --- | --- | --- |
| `v` | версия схемы | `1` |
| `seq` | порядковый номер в журнале, ставит хаб | `184467` |
| `id` | id события в журнале (ULID) | `01JD…` |
| `owner` | чей это (пользователь хаба) | `u_…` |
| `org` | организация, если есть | `o_…` |
| `type` | `<домен>.<что>` | `chat.message`, `issue.assigned`, `mr.review_requested`, `mail.received`, `job.done` |
| `source` | откуда | `telegram-account`, `gitlab`, `mcp:higgsfield`, `harnessly`, `app:<id>` |
| `connection` | подключение человека | `c_…` |
| `ext` | id вещи у источника | Message-ID, id задачи, guid |
| `at` | когда случилось у источника | RFC 3339 |
| `actor` | кто сделал | `@ann`, `Ann <ann@…>` |
| `url` | где открыть | ссылка |
| `thread` | разговор или задача, к которой относится | `tg:-100…`, `issue:ABC-12` |
| `ref` | чем агент читает целиком | `item id=…` |
| `mine` | сделал сам человек | `true` |
| `facts` | короткие факты для фильтров, до 12 | `{"hasAttachment":"true"}` |
| `via` | каким путём пришло (может быть несколько после склейки) | `["webhook","poll"]` |
| `machine` | машина, которая держит текст события | `m_…` |

**Текста в хабе нет.** Заголовка, тела, выдержки в журнале нет, как и сегодня в автоматизациях (`textKeys`): текст
письма или сообщения остаётся на машине человека. Подписчику, которому текст нужен (дайджест, виджет), его доставляет
**машина**: хаб говорит машине «отдай событие N подписчику S», машина прикладывает заголовок из своего журнала и
доставляет. Так инвариант «текст не покидает машину без нужды» сохраняется при одном реестре подписок в хабе. Событие
источника без машины (вебхук сервиса прямо в хаб) текста не несёт вовсе: подписчик читает его по `ref` или `url`.

### Журнал

Таблица `bus_events`: только дописывается. `seq` — автоинкремент, по нему читают курсоры. Уникальность по
`(owner, fingerprint)`, где `fingerprint` = источник + `ext` (как `connectors.Fingerprint`): одно и то же событие,
пришедшее вебхуком и опросом, — одна строка, вторая дописывает себя в `via`. Хранение — 30 дней по умолчанию
(`HUB_BUS_RETENTION`), чистит лидер.

### Подписки

Таблица `bus_subscriptions`: владелец, потребитель (`rules`, `inbox`, `notify`, `widget`, `job`, `app:<id>`,
`webhook`), фильтр (типы, источники, подключения, факты, `mine`), курсор `seq`, состояние, счётчик ошибок.

- **Доставка «хотя бы раз», по порядку внутри подписки.** Потребитель подтверждает — курсор двигается. Не подтвердил —
  повтор с паузой (1 с, 5 с, 30 с, 5 мин), после 8 неудач подписка встаёт в `failing` и видна в UI.
- **Потребитель идемпотентен по `id` события** — это контракт, а не пожелание.
- **Новая подписка** начинает с текущего конца журнала; с прошлого — только явно (`from: <seq>` или `from: "-24h"`).
- **Одна доставка на кластер.** Раздаёт только лидер (`internal/hub/leader`); остальные реплики будят его
  `NOTIFY` при записи. На SQLite одна реплика, она же лидер.

### Каталог триггеров

`bus_triggers`: каждый вид события — источник, подключение, тип — становится триггером человека с первым
событием, в положении `digest`. Настраивать заранее ничего не нужно: всё по умолчанию попадает в журнал и в дайджест.
Человек меняет положение на странице `/events`, вкладка «Триггеры», или `PUT /events/triggers`:

| Положение | Что делает хаб |
| --- | --- |
| `digest` | пишет в журнал; дайджест берёт его сам (по умолчанию) |
| `notify` | и сразу звонит в колокольчик владельца (свой подписчик хаба `modes`) |
| `agent` | и ставит запуск агента: одно правило автоматизаций на триггер с источником `bus`, которого не бывает у событий снаружи; отпечаток запуска — id события, повторная доставка запускает один раз |
| `off` | событие отбрасывается до журнала (`ErrOff`), но считается в каталоге |

Триггер можно выключить и до первого события. Правила автоматизаций, заведённые человеком явно, положение не трогает.

### Источники

| Источник | Как попадает в шину |
| --- | --- |
| Коннектор машины | `automations.event` по связи машины, как сейчас; хаб пишет в журнал, затем раздаёт |
| Вебхук сервиса | хаб регистрирует его сам при подключении, если хватает прав; адаптер сервиса превращает тело в Event v1 |
| Подписка MCP | хаб держит сессию с сервером, по `resources/updated` перечитывает и сравнивает |
| Рецепт опроса MCP | агент пишет рецепт при подключении, хаб исполняет без модели |
| harnessly | свои события: чат закончил, агент ждёт, MR влит, регулярная задача отработала |
| SDK `emit` | приложение или плагин с правом `events:emit` по своему токену |
| Расписание и ожидание | срабатывание — тоже событие (`schedule.fired`, `wait.expired`), видно в журнале |

### Потребители

Автоматизации — синхронный потребитель на входе, и так и остаются: каждое событие, которое они принимают (`/hook`,
`automations.event` машины, срабатывание расписания и ожидания), сначала пишется в журнал, затем правила сопоставляются
как раньше, и `/hook` по-прежнему отвечает, какие запуски поставил. Отказ журнала правила не останавливает. Подпиской
шины правила не становятся сознательно: промпту правила нужно тело вебхука (заголовок и описание алерта), а журнал текста
не хранит. Положение триггера `agent` — это и есть правило, которое живёт на шине. «Входящие» вместо `/api/ingest` получают подписку `inbox` (через машину, с
заголовком). Уведомления, виджеты в чате, задачи по триггеру, `subscribe` в SDK и вебхук наружу — новые подписчики.

## Уровни

Журнал сегментирован по уровням хаба, не по источникам: у события есть владелец, пространство (машины, с которой оно
пришло) и организация (этого пространства), и **видимость**.

| Видимость | Что | Кто видит |
| --- | --- | --- |
| `person` | переписка: `mail.*`, `chat.*`, `message.*`, `calendar.*`, `meeting.*`, `note.*`, `file.*`, `contact.*`, `call.*`, `dm.*` | только владелец |
| `team` | всё остальное: задачи, MR, CI, алерты, вебхуки сервисов, расписания | владелец, участники пространства, админы организации |

Видимость ставит хаб по домену типа. Источник может сузить событие до владельца, но не может расширить переписку до
команды: даже конверт без текста говорит, кто кому и когда писал.

| Уровень (`?scope=`) | Кому открыт | Что в нём |
| --- | --- | --- |
| `me` | каждому | свои события любой видимости |
| `space:<id>` | участнику пространства | свои плюс `team`-события пространства |
| `org:<id>` | админу организации | свои плюс `team`-события всех пространств организации |
| `all` | админу хаба | весь журнал |
| `deployment` | админу хаба | события самой установки (общий `/hook`) |

Список доступных человеку уровней — `GET /events/scopes`. Просьба уровня выше своего — отказ `403 scope`, а не пустая
страница. SDK получает те же уровни по личному токену с областью `events`: её человек отмечает явно, когда подключает
приложение (`/connect`), по умолчанию она не выдаётся. Токен читает ровно то, что может его человек.

## Страница `/events`

Журнал вживую на хабе: сначала последние 200 событий, затем поток (`/events/stream`, SSE) с того места, где они
кончились, — ничего не теряется между ними, а переподключение продолжает с `Last-Event-ID`. Новые события появляются
сверху с подсветкой; «Раньше» дочитывает прошлое; пауза копит пришедшее и выкладывает разом. Выбор уровня, поиск по
типу, источнику, автору, ветке и фактам, фильтр по домену. Клик по событию — его конверт и **цепочка**: события той же
ветки (`thread`), от первого к последнему. Вкладка «Подписки» — кто читает журнал, насколько отстаёт, последняя ошибка,
пауза и перечитывание; админ хаба видит и подписки самого хаба.

## API

Права — владелец или его токен с нужной областью.

| Маршрут | Что |
| --- | --- |
Под `<platform api>/events` (по умолчанию `/api/platform/events`).

| Маршрут | Этап | Что |
| --- | --- | --- |
| `GET /events?after=&type=&source=&limit=` | 1 | журнал человека страницами по `seq`; `next` — `after` следующей страницы; админ хаба читает события самой установки с `?owner=deployment` |
| `GET /events/subscriptions` | 1 | подписки человека с курсором, состоянием и последней ошибкой |
| `POST /events/subscriptions/{id}/replay` `{after}` | 1 | перемотать курсор |
| `POST /events/subscriptions/{id}/pause`, `/resume` | 1 | остановить и продолжить доставку |
| `GET /events/scopes` | 1 | уровни, открытые человеку, и `head` журнала |
| `GET /events?scope=&before=` / `?newest=1` | 1 | то же назад, от новых к старым |
| `GET /events/stream?scope=&after=` | 1 | журнал вживую (SSE): `id` — `seq`, `event: bus`; продолжает с `Last-Event-ID` |
| `POST /events` | 4 | `emit` из SDK и приложений |
| `GET/PUT /events/triggers` | 2 | каталог и положения |

CLI: `harnessly events tail|emit|subs|triggers`. SDK (`extsdk`): `events.emit`, `events.subscribe`.

## Флаг и порядок выката

Флаг `HUB_EVENT_BUS` (выключен — всё как раньше). Миграции только добавляют таблицы, предыдущий релиз их не читает.

1. Журнал и Event v1; все входы автоматизаций пишут в журнал; правила — подписчик `rules`. `events tail`.
2. Каталог триггеров и четыре положения; журнал в UI.
3. Доставка через машину с текстом; «Входящие» — подписчик вместо `/api/ingest`.
4. Источники: автоматические вебхуки сервисов, рецепты опроса MCP, подписки MCP, свои события harnessly.
5. Потребители: уведомления, виджет в чате, задачи по триггеру, SDK, вебхук наружу. Защита от шума.

## Чего шина не делает

- не хранит текст событий;
- не запускает модель: всё на шине детерминированно, модель — только у потребителей (разбор, агент);
- не заменяет брокер сообщений между сервисами: это журнал событий людей, а не транспорт инфраструктуры. Если объём
  потребует, курсорная модель переносится на внешний брокер без изменения подписчиков.
