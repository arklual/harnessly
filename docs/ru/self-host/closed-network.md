# Развёртывание в закрытом контуре

Для сети без интернета, со своим корпоративным CA, прокси и внутренними доменами. На странице — все адреса, которые
harnessly может открыть, и что с каждым делать: отдавать изнутри, пускать через прокси или выключить. Имена в примерах —
`example.corp`.

## Что уходит с машины

| Кто | Адрес | Зачем | В закрытом контуре |
| --- | --- | --- | --- |
| `install.sh` | `raw.githubusercontent.com`, `github.com/ly-solutions/harnessly/releases` | установщик и архивы релиза | Ставьте с хаба: `curl <хаб>/install \| sh -s -- --token …`, программы приходят с `/dl` хаба. Без хаба — [офлайн-пакет](../../hub/machine.md) (`--offline`) или `--mirror` |
| установщик | `claude.ai/install.sh` | Claude Code | Поставьте Claude Code сами (из своего источника пакетов); проверка «Claude Code / Codex» в настройках скажет, если его нет |
| рантайм | `<хаб>/dl/…` | обновление программ машины | Внутри: хаб. `RUNTIME_UPDATE_CHECK_URL` — зеркало GitHub API |
| рантайм | `huggingface.co`, `cdn.jsdelivr.net` | встроенный голосовой ввод: файлы модели и движок в браузере | Зеркало с теми же путями внутри и `RUNTIME_VOICE_MODEL_HOST`, `RUNTIME_VOICE_RUNTIME_HOST`; либо не включайте голос (пока его не включили, адреса не открываются) |
| рантайм | `storage.googleapis.com/chrome-for-testing-public` | Chrome браузера агента | `RUNTIME_BROWSER=off` или свой Chrome и путь в `RUNTIME_BROWSER` |
| агент | `api.anthropic.com`, `api.openai.com` | модель Claude Code / Codex | Свой шлюз моделей: см. «Провайдер моделей» |
| дизайн | `unpkg.com` (React, Babel) | скрипты движка дизайна | Ничего: React и Babel отдаются из бинаря, на unpkg идёт только релизный движок других версий |
| демо-проекты | `fonts.googleapis.com` | образцы презентаций и сайтов | Косметика: страница берёт системные шрифты. Демо можно удалить |
| Подключения | хосты подключённых сервисов (`github.com`, свой GitLab, …) | доски, репозитории, документы | Только то, что подключили; внутренние сервисы — в политике контура ниже |
| приложения | то, что назвал `.mcp.json` приложения | бэкенд приложения | Ваш сервис; указывается в политике контура ниже |
| хаб | ваш OIDC-провайдер, ваш SMTP | вход | Внутри: см. «Вход в хаб» |

`harnessly selftest` и «Проверка машины» (Настройки → Общие) показывают, что из этого машина достаёт.

## Политика контура

Одна политика говорит, куда можно ходить приложениям и Подключениям. Её держит хаб, машины забирают сами.

Положите `network.json` в папку dist хаба (`HUB_DIST_DIR`, `/opt/harnessly/dist`):

```json
{
  "internalHosts": ["*.example.corp", "crm.example.corp"],
  "caPem": "-----BEGIN CERTIFICATE-----\n…\n-----END CERTIFICATE-----\n",
  "proxy": "http://proxy.example.corp:3128",
  "noProxy": ["localhost", ".example.corp"]
}
```

| Ключ | Смысл |
| --- | --- |
| `internalHosts` | имена (`crm.example.corp`) и суффиксы (`*.example.corp`), которым можно быть на частных адресах; им разрешён и обычный `http`; link-local адреса (облачные метаданные) закрыты всегда |
| `caPem` | ваши корневые сертификаты, добавляются к системным |
| `proxy` | прокси для вызовов приложений и Подключений |
| `noProxy` | хосты в обход прокси: имена, `.суффикс`, `*.суффикс`, IP, CIDR |
| `publishers`, `requireSigned` | кто может подписывать пакеты приложений (`{"name", "key"}`) и обязательна ли подпись (ниже) |

Хаб отдаёт файл по `/dl/network.json` (без входа, как программы: секретов в нём нет) и отвергает файл, который не
проходит проверку. Машина читает его при старте и раз в пять минут, последнюю версию хранит в папке данных
(`network-policy.json`), поэтому после перезапуска без хаба политика остаётся.

**Окружение машины главнее.** Что названо в окружении, заменяет значение хаба для этой настройки; что не названо,
берётся с хаба:

| Переменная | Настройка |
| --- | --- |
| `RUNTIME_APPS_INTERNAL_HOSTS` | `internalHosts` |
| `RUNTIME_APPS_CA_FILE` | корневые сертификаты (PEM-файл) |
| `RUNTIME_APPS_PROXY`, `RUNTIME_APPS_NO_PROXY` | `proxy`, `noProxy` |
| `RUNTIME_APPS_CLIENT_CERT_FILE`, `RUNTIME_APPS_CLIENT_KEY_FILE` | клиентский сертификат для mTLS: уходит, когда сервер его просит |

**Правьте в хабе, а не файлом.** Администратор установки открывает **Аккаунт → Закрытый контур** (`/network`) и заполняет
форму: внутренние домены, корневые сертификаты, прокси и исключения, правило о подписи. Форма проверяет ввод и говорит,
какое поле неверно и что написать; политика с ошибкой не сохраняется. Сохранение пишет `network.json` в папку dist (тот же
файл, что выше), и машины подхватывают его сами: они спрашивают хаб раз в пять минут, перезапуск не нужен. То же самое
делают `GET`/`PUT /api/admin/network` для администратора.

`install.sh --ca-file`, `--proxy` и `--no-proxy` пишут эти переменные для рантайма, а для всех компонентов — ещё
`SSL_CERT_FILE` и `HTTPS_PROXY`. При повторном запуске установщик сохраняет строки, которых сам не пишет (ваши
`RUNTIME_PREVIEW_DOMAIN`, `RUNTIME_APPS_INTERNAL_HOSTS`).

Вызов приложения через прокси проверяется так же, как прямой: машина сама разрешает имя, каждый полученный адрес должен
пройти политику, а туннель (`CONNECT`) открывается на проверенный адрес, а не на имя. Внутренний домен, который машина
разрешить не может (его знает только прокси), идёт в прокси по имени. Хост, записанный числом не в канонической форме
(`2130706433`, `0x7f.1`, `127.1`), отклоняется. Вызовы `http://` тоже идут в прокси через `CONNECT`. Отказ по политике
говорит об этом словами: «домен `crm.example.corp` не в политике контура — попросите администратора добавить его во
внутренние домены» (в ответе моста есть поле `hint`).

## DNS для превью

Превью dev-сервера идёт по пути на адресе самой страницы (одно имя, один сертификат, в DNS ничего заводить не нужно):
рантайм за хабом делает так сам. Для слотов на собственных именах задайте домен — рантайм соберёт из него восемь
адресов `https://s1-<id>.<домен>` … `s8-<id>.<домен>`, одинаковых после каждого перезапуска:

```sh
RUNTIME_PREVIEW_DOMAIN=pv.example.corp
RUNTIME_PREVIEW_ID=m1               # необязательно: по умолчанию id машины
```

DNS: одна wildcard-запись `*.pv.example.corp` → машина (или ваш реверс-прокси перед портами `8023`–`8030`) и
wildcard-сертификат; подробности — в [Развёртывании](../../deploy.md). `harnessly doctor preview` и проверка машины
«preview_dns» скажут, если имя слота не резолвится, — с записью, которую завести.

## Корпоративный CA

- `install.sh --ca-file /path/ca.pem`: загрузки и все компоненты ему доверяют.
- `caPem` политики или `RUNTIME_APPS_CA_FILE`: вызовы приложений и Подключений.
- Claude Code или git, которые ходят на ваши серверы: `SSL_CERT_FILE` / `NODE_EXTRA_CA_CERTS` (установщик их ставит).

## Вход в хаб

Используйте свой OpenID Connect-провайдер (корпоративный Keycloak, Authentik, …): `HUB_OIDC_PROVIDERS` и
`HUB_OIDC_<ID>_*` (см. [Запуск хаба](../../hub/deploy.md)); вход по коду из письма отключается `HUB_AUTH_EMAIL=off`, если
почты нет. Хаб забирает ключи провайдера: ему нужен адрес провайдера, ваш CA и, если есть, прокси.

## Провайдер моделей

Агенту нужна модель. Дайте машинам профиль модели, у которого `base_url` — ваш шлюз (https, см.
[профили моделей](../../model-profiles.md)). harnessly сам к хостам моделей не ходит — ходит агент, поэтому шлюз и его
сертификат должны быть доступны с машины.

## Приложения и каталог

- **Командный каталог на хабе — основной путь** в закрытом контуре: `harnessly app publish ./app --channel stable` кладёт
  пакет в каталог команды, `harnessly app install --team <id>` и элементы окружения `app` отдают его машинам. Снаружи
  ничего не скачивается.
- **Публичному каталогу нужен интернет**: не пользуйтесь им.
- **Перенос пакета через шлюз:** упакуйте пакет в файл, перенесите файл, поставьте с другой стороны.
  `harnessly app validate ./папка --strict` заранее скажет, что не так; `harnessly app pack ./папка` пишет
  `<id>-<версия>.hlapp`; `harnessly app install ./файл.hlapp` ставит его. Подпишите пакет, чтобы другая сторона знала, чей
  он (ниже).
- **Бэкенд приложения** — ваш сервис (`.mcp.json` с `type: http`): его хост — в `internalHosts`; доверие даёт ваш CA, а
  собственный клиентский сертификат приложения делает вызов mTLS (ниже).

### Клиентский сертификат на приложение

Бэкенд банка часто просит клиентский сертификат. Дайте его приложению, которое с ним говорит, а не всей машине:

```json
{
  "permissions": ["secrets:bank-mtls"],
  "secrets": [{ "name": "bank-mtls", "description": "Клиентский сертификат и ключ для crm.example.corp, PEM" }],
  "network": { "clientCert": { "secret": "bank-mtls", "hosts": ["crm.example.corp"] } }
}
```

- Сертификат и ключ — один PEM в секрете приложения `bank-mtls`: человек (или администратор) вставляет его при установке,
  он лежит в сейфе машины, а не в манифесте и не в пакете.
- Он уходит только на хосты собственных MCP-серверов этого приложения (`.mcp.json`); `hosts` сужает до части из них. На
  другие хосты он не уходит и другому приложению не достаётся. Сертификат всей машины (`RUNTIME_APPS_CLIENT_CERT_FILE`)
  остаётся как был для приложений, которые своего не назвали.
- Значения ещё нет или это не сертификат с ключом: вызовы приложения ждут и говорят об этом словами, без сертификата они
  не уходят.

### Подпись пакетов (`.hlapp`)

`.hlapp` — пакет одним файлом; рядом `ФАЙЛ.hlapp.sig` — подпись издателя (ed25519 от SHA-256 файла).

1. Издатель один раз делает ключ: `harnessly app key --out key.txt` печатает **открытый ключ** и пишет закрытый в `key.txt`
   (0600). Положите его в сейф (`harnessly secret ask hlapp-signing-key`, вставьте содержимое файла) и удалите файл.
2. Издатель подписывает: `harnessly secret run --env HLAPP_SIGNING_KEY=hlapp-signing-key -- harnessly app pack ./app --sign
   --publisher "Example Bank"`. Ключ есть в процессе, только пока он работает.
3. Администратор добавляет открытый ключ издателя в **Закрытый контур → Подпись приложений** (или в `publishers` файла
   `network.json`: `{"name": "Example Bank", "key": "<base64>"}`) и включает **Требовать подпись** (`requireSigned`, или
   `RUNTIME_APPS_REQUIRE_SIGNED=1` на одной машине).
4. `harnessly app install ./app.hlapp` сначала проверяет подпись. Отказ говорит почему, словами:
   - без подписи: «пакет не подписан, а в этом контуре устанавливаются только подписанные приложения»;
   - не тот издатель: «подпись не от доверенного издателя: пакет подписан «X» (ключ …), а в контуре доверяют другим
     издателям — попросите администратора хаба добавить этот ключ»;
   - изменён после подписи: «подпись не сходится с пакетом: пакет изменили после подписи» — отказ всегда, нужна подпись
     или нет.

Подписанный `.hlapp` можно публиковать прямо из файла: `harnessly app publish ./app.hlapp --channel stable --team`
проверяет подпись и хранит её вместе с версией; каталог команды и публичный каталог несут её дальше, а машины, которые
получают приложение, проверяют её снова. Подпись хранит только `stable`: предрелизный канал переписывает версию в
манифесте, а подпись её не покрывает, поэтому такая версия публикуется без подписи. Где подпись не обязательна, пакет
без подписи ставится как раньше.

Где подпись обязательна, **ни один** путь установки не обходит проверку: папка (`harnessly app install ./папка`), канал
(`--channel`, следование за каналом), каталог команды, публичный каталог и приложения окружения отказывают, если пакет не
подписанный `.hlapp` доверенного издателя. Папка, установленная для разработки (`harnessly app dev`), — собственная работа автора и не проверяется. Где подпись
обязательна, команда говорит об этом словами и пишет `install.dev-unsigned` в журнал приложения: исключение осознанное и
видное.
