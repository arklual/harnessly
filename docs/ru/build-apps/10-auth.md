# Вход: кто вызывает ваш бэкенд

Удалённому MCP-серверу приложения (`.mcp.json`, `url`) часто надо знать, кто его вызывает: показать человеку его данные,
проверить права, записать строку аудита. Хост входит за вас. Вид никогда не держит токен, MCP-клиент агента тоже: хост
сам добавляет токен в вызовы, которые делает за них.

## Выберите способ

| Способ | `.mcp.json` | Что получает бэкенд | Когда подходит |
| --- | --- | --- | --- |
| Токен платформы | `"auth": {"type": "platform"}` | `Authorization: Bearer <JWT>`, подписанный хабом: человек, его организация и команда, приложение | Бэкенд ваш, нужно «кто это» без своего входа. Большинство случаев |
| Токен корпоративного SSO | `"auth": {"type": "oidc"}` | `Authorization: Bearer <токен вашего провайдера входа>` для вашего бэкенда, полученный обменом токена | Бэкенд уже доверяет SSO компании (Keycloak, ADFS…) и ничему другому доверять не должен |
| Вход по OAuth | `"auth": {"type": "oauth"}` | Токен, который человек получил, войдя в ваш сервер (MCP authorization: discovery, регистрация, PKCE) | У сервера свой OAuth, как у SaaS |
| Секрет | `"headers": {"X-Api-Key": "${secret:key}"}` (или `"auth": {"type": "secret"}`) | Ключ установки, один на всех | Сервисный ключ, за ним нет человека |
| Подключение | `"connection": "<id из каталога>"` | Подключение самого человека (Настройки → Подключения) | Известный сервер из каталога |

`auth` стоит рядом с `url` в описании сервера:

```json
{
  "mcpServers": {
    "crm": {
      "type": "http",
      "url": "https://crm.internal.example/mcp",
      "auth": { "type": "platform" }
    }
  }
}
```

`aud` токена платформы — всегда origin самого сервера (`https://host[:port]`): приложение не может попросить токен для
чужого бэкенда и получить его на свой адрес. Для `oidc` поле `audience` называет аудиторию вашего бэкенда у провайдера
входа (по умолчанию origin), и хаб меняет токен только на те аудитории, которые администратор разрешил для этого адреса.
`scope` передаётся провайдеру входа для `oidc` и `oauth`. У сервера с `auth` (кроме `secret`) нет своего заголовка `Authorization`; `harnessly app check` об этом
скажет.

## Токен платформы

JWT, подписанный Ed25519-ключом хаба (`alg: EdDSA`, `typ: harnessly-app+jwt`), живёт 5 минут. Хост держит его это время и
берёт новый за минуту до конца; если бэкенд ответил 401, хост берёт свежий токен и повторяет вызов один раз.

| Поле | Что значит |
| --- | --- |
| `iss` | Адрес хаба (`https://harnessly.example`). Машина без хаба: `urn:harnessly:machine:<host>` |
| `sub` | Постоянный id человека в хабе. Ключуйте данные по нему, не по почте |
| `aud` | Ваш бэкенд (`audience`). Любой другой отвергайте |
| `exp`, `iat`, `nbf`, `jti` | Время и id токена |
| `email`, `name` | Для показа и логов |
| `org`, `space` | Организация и команда человека в хабе |
| `app`, `server` | Приложение и его сервер, для которых вызов |
| `machine` | Машина, которая попросила |

**Где ключи.** Хаб публикует их по адресу `https://<хаб>/.well-known/jwks.json` (кэш 5 минут; после смены ключа старый
остаётся в наборе). Машина без хаба подписывает своим ключом и ничего в сеть не публикует: набор лежит в
`app-token.jwks.json` в папке данных рантайма, администратор бэкенда копирует его к себе.

**Проверка на бэкенде**: подпись ключом из набора, `iss`, свой `aud` и `exp` — всегда; `typ` — где библиотека позволяет.

Go (`github.com/coreos/go-oidc/v3`):

```go
keys := oidc.NewRemoteKeySet(ctx, "https://harnessly.example/.well-known/jwks.json")
verifier := oidc.NewVerifier("https://harnessly.example", keys, &oidc.Config{
	ClientID:             "https://crm.internal.example", // ваша аудитория
	SupportedSigningAlgs: []string{oidc.EdDSA},
})

func whoCalls(r *http.Request) (string, error) {
	raw, ok := strings.CutPrefix(r.Header.Get("Authorization"), "Bearer ")
	if !ok {
		return "", errors.New("no token")
	}
	tok, err := verifier.Verify(r.Context(), raw) // подпись, iss, aud, exp
	if err != nil {
		return "", err
	}
	var c struct {
		Email string `json:"email"`
		App   string `json:"app"`
	}
	_ = tok.Claims(&c)
	return tok.Subject, nil
}
```

Node (`jose`):

```js
import { createRemoteJWKSet, jwtVerify } from 'jose';

const keys = createRemoteJWKSet(new URL('https://harnessly.example/.well-known/jwks.json'));

export async function whoCalls(req) {
  const raw = (req.headers.authorization ?? '').replace(/^Bearer /, '');
  const { payload } = await jwtVerify(raw, keys, {
    issuer: 'https://harnessly.example',
    audience: 'https://crm.internal.example',
    typ: 'harnessly-app+jwt',
    algorithms: ['EdDSA'],
  });
  return { id: payload.sub, email: payload.email, org: payload.org, app: payload.app };
}
```

На токен, который вы не принимаете, отвечайте `401` с `WWW-Authenticate: Bearer error="invalid_token"`, человеку без
доступа — `403`: хост превратит их в коды ниже.

**Почему подписывает хаб, а не машина.** Хаб знает, кто человек (владелец машины, вошедший через SSO организации), его
организацию и команду; один ключ на развёртывание — один JWKS для всех бэкендов, а не по одному на машину; и у хаба есть
клиент в провайдере входа, нужный для обмена токена. Машина ключа не держит: она просит хаб запросом, подписанным своим
ключом, и токен приходит запечатанным для неё.

## Корпоративный SSO: обмен токена

С `"auth": {"type": "oidc"}` хаб отдаёт вашему провайдеру входа токен платформы, выписанный для провайдера, и получает
взамен его собственный токен доступа для вашего бэкенда (RFC 8693,
`grant_type=urn:ietf:params:oauth:grant-type:token-exchange`). Бэкенд видит токен банка, как будто человек вошёл в него
напрямую, и проверяет его ключами провайдера, как уже умеет. Токенов собственного входа человека хаб не хранит.

Настраивает администратор хаба:

| Переменная | Что значит |
| --- | --- |
| `HUB_APP_TOKEN_EXCHANGE_URL` | Token endpoint провайдера |
| `HUB_APP_TOKEN_EXCHANGE_CLIENT_ID`, `HUB_APP_TOKEN_EXCHANGE_CLIENT_SECRET` | Клиент хаба у провайдера (HTTP Basic) |
| `HUB_APP_TOKEN_EXCHANGE_AUDIENCE` | `aud` токена платформы, который получает провайдер; по умолчанию client id |
| `HUB_APP_TOKEN_EXCHANGE_AUDIENCES` | Обязательно. `аудитория=https://бэкенд[:port]` через запятую: какую аудиторию провайдера можно отправлять на какой бэкенд. Всё прочее отклоняется (`auth_denied`) ещё до запроса к провайдеру |
| `HUB_APP_TOKEN_EXCHANGE_SCOPE` | Scope по умолчанию |
| `HUB_APP_TOKEN_EXCHANGE_SUBJECT_TOKEN_TYPE` | По умолчанию `urn:ietf:params:oauth:token-type:jwt` |

На стороне провайдера хаб — доверенный внешний издатель: его JWKS (`/.well-known/jwks.json`), его `iss` и поле, которое
называет человека (`email` или `sub`). В Keycloak это провайдер идентичности типа «OpenID Connect v1.0» или «JWT» с
разрешённым обменом токена для клиента хаба и аудитории бэкенда.

## Ключи платформы

| Переменная | Что значит |
| --- | --- |
| `HUB_APP_TOKEN` | `on` (по умолчанию) или `off`: хаб не выдаёт токены и не публикует JWKS |
| `HUB_APP_TOKEN_KEY_FILE` | Ключ Ed25519, PKCS#8 PEM; создаётся при первом старте (`<HUB_DATA_DIR>/app-token.pem`). Все реплики читают один файл |
| `HUB_APP_TOKEN_PREVIOUS_KEYS` | Через запятую — публичные ключи (PKIX PEM) прошлых ротаций, ещё публикуются |

Смена ключа: новый ключ в `HUB_APP_TOKEN_KEY_FILE`, старый публичный — в `HUB_APP_TOKEN_PREVIOUS_KEYS`, перезапуск;
через 10 минут старый можно убрать.

## Вход по OAuth в ваш сервер

С `"auth": {"type": "oauth"}` человек входит в сам ваш сервер так же, как в подключение: хост находит сервер авторизации
(MCP authorization), регистрируется клиентом, проводит code flow с PKCE во всплывающем окне верхнего уровня и хранит
токен в сейфе. Вход принадлежит приложению: подключение человека к тому же адресу для него не используется, а сам вход —
только для сервера этого приложения. Вход виден в Настройки → Подключения, там из него можно выйти; для остальных агентов человека он выключен —
они ходят в сервер только через приложение. Пока человек не вошёл, вызовы отвечают `auth_required` с
`error.signIn = {app, server}`, и хост показывает «Войти».

## Когда вход не удался

| Код | Когда | Что видит человек | Что читает агент |
| --- | --- | --- | --- |
| `auth_required` | Входа нет: сервер ответил 401 на вызов без учётных данных; подключение не создано или в него не вошли; в сервер `oauth` ещё никто не вошёл | «Войти» на карточке приложения | `the server wants a sign-in: sign in, then repeat the call` и `error.signIn` |
| `auth_expired` | Вход больше не принимается: 401 на вызов с токеном (после одного свежего токена), токен истёк и не обновился | «Войти снова» | `the server no longer takes the sign-in: sign in again, then repeat the call` |
| `auth_denied` | Вошёл, но отказано: 403, `insufficient_scope`, провайдер отказал в обмене | Доступ даёт администратор сервера | `the server refuses this to the signed-in person: ask its admin for access` |
| `idp_unreachable` | Провайдер входа (его token endpoint) не ответил | Повторить позже | `the sign-in service did not answer: try again later` |
| `host_unavailable` | Хаб не ответил за токеном, или развёртывание не выдаёт токен этого вида (`HUB_APP_TOKEN=off`, обмен не настроен) | Это настраивает администратор | В сообщении названы `HUB_APP_TOKEN_*` |

`error.signIn` говорит, где вход это исправит: `{connection}` для подключения, `{app, server}` для сервера `oauth`.
Слова самого сервера и его `WWW-Authenticate` остаются в логе машины и никогда не попадают в вид.

## Правила хоста

- Токен не попадает ни во вид, ни в контекст агента, ни в лог: хост добавляет его в свой запрос.
- Токен платформы живёт 5 минут (максимум 10) и называет в `aud` сервер, куда его отправляют; бэкенд обязан отвергать
  любой другой. Токен провайдера уходит только на бэкенд, который администратор хаба указал для его аудитории.
- Отказанный вызов повторяется со свежим токеном не больше одного раза.
- Ключи и клиент обмена — у хаба; на машине их нет.
