# Хранилище

Хранилище держит главную копию данных людей в хабе (первой — библиотеку Sinopia), а на машине лежит рабочая копия.
Файл — это цепочка ревизий в базе, содержимое — блобы по sha256. Правка на одной машине за секунды доходит до
остальных машин пространства. Машина, которая была выключена, догоняет, когда снова включится. Запись, сделанная
поверх устаревшей копии, не теряется, а откладывается рядом с файлом.

Хранилище есть всегда. Рантайм без хаба держит его внутри своего процесса: SQLite и папка в каталоге данных, та же
модель. Хаб, подключённый позже, может забрать эти данные к себе (`hub store migrate`).

## Коллекции

У каждого пространства свои коллекции. Машина видит только коллекции своего пространства.

| Коллекция | Что в ней |
| --- | --- |
| `design` | библиотека Sinopia: проекты, доски, артефакты. Скрытые файлы не синхронизируются, кроме `.owner.json` проекта и полок в `.folders/` |
| `uploads` | файлы, которые люди положили в чат: картинки и вложения |
| `files` | любые другие файлы агента или человека |
| `handoff` | то, что одна машина передаёт другой |
| `apps` | файлы приложений пространства |

`design` принимает только файлы библиотеки: без исполняемых файлов и настроек инструментов. Остальные коллекции
принимают любой относительный путь. Коллекция — это комната хранилища с именем `<коллекция>-<id пространства>`.

## Как машина подключается

1. Рантайм читает `GET /api/capabilities` хаба. Если возможности `store` нет (старый хаб или `HUB_STORE=off`),
   он ведёт себя по-старому и переспрашивает раз в десять минут.
2. Он просит сессию: `POST /agent/store` с подписью собственным ключом машины Ed25519. Это тот же ключ, которым
   машина подключается к хабу (`machine.json`). Токены никто не выдаёт. Машина, которую отозвали, выключили или
   перенесли в другое пространство, теряет доступ к хранилищу в течение тридцати секунд, даже с действующей сессией.
3. Сессия живёт час. Новую рантайм просит заранее или после ответа 401. С сессией он работает с API хранилища по
   адресу `/store/v1/collections/<коллекция>/`.

| Метод и путь | Что делает |
| --- | --- |
| `HEAD`, `GET`, `PUT blobs/<sha256>` | блоб: есть ли он, прочитать, положить (хэш тела должен совпасть с именем) |
| `POST blobs/missing` | `{shas: […]}` (не больше 500): каких из этих блобов в коллекции нет, `{missing: […]}`. Один запрос перед пачкой загрузок вместо `HEAD` на каждый; права проверяются так же, как у `HEAD` |
| `POST commit` | новая ревизия пути поверх той, с которой начинал автор (`base`). На устаревшую базу ответ `409` с текущей ревизией |
| `GET changes?since=<rev>&wait=<s>` | все пути, изменённые после ревизии. С `wait` запрос ждёт, пока что-нибудь изменится (долгий опрос) |
| `GET current?path=<p>` | последняя ревизия пути |
| `GET history` | ревизии пути |
| `GET`, `POST leases`, `POST leases/release` | кто сейчас правит какую доску |
| `GET health` | хранилище отвечает |

Блоб, прочитанный по хэшу, никогда не меняется. Он отдаётся с `ETag` и вечным кэшем.

## Запись поверх устаревшей копии

Хаб принимает запись только поверх ревизии, с которой начинал автор. Если две машины меняют один файл, вторая не
затирает первую. На месте файла остаётся версия хаба, а проигравшее содержимое попадает в
`.conflicts/<путь>.<машина>.<время>` в библиотеке, рядом с уведомлением. Рантайм сообщает об этом агенту, который
писал файл. Маленькая правка доски только откладывается, чтобы агент применил её заново. Большая правка ещё и
сохраняется отдельным проектом `<проект>-variant-…`.

## Рантайм

`RUNTIME_STORE` выбирает, где хранилище рантайма ([настройка](../../configuration.md#design-library)):

| Значение | Что происходит |
| --- | --- |
| `auto` (по умолчанию) | машина хаба (`machine.json` в каталоге данных) синхронизируется с хранилищем своего хаба. Рантайм в паре с агентом кластера (`AGENT_SECRET_FILE` или `AGENT_CLUSTER_URL`) оставляет данные как есть. Одиночный рантайм держит хранилище внутри себя |
| `hub` | только хранилище хаба. Машина не из хаба ничего не синхронизирует |
| `embedded` | хранилище внутри процесса, что бы ещё ни было |
| `off` | ничего не синхронизируется |

Хранилище внутри рантайма лежит в `<каталог данных>/store`. Что синхронизация знает о каждой папке — в
`<каталог данных>/store-sync`. Папка библиотеки может переехать (другое рабочее пространство): синхронизируется та
папка, где библиотека сейчас.

## Драйверы

| | Ревизии | Содержимое |
| --- | --- | --- |
| По умолчанию | SQLite в `HUB_STORE_DIR` (`<HUB_DATA_DIR>/store`) | та же папка |
| Хаб на Postgres | база хаба, в отдельных таблицах (`filestore_rooms`, схемы `filestore_r_*`). Если задан `HUB_DB_MIGRATE_URL`, хранилище ходит через него: схемам нужен `search_path` сессии, а пулер в режиме транзакций его теряет | |
| `HUB_STORAGE=s3` | | бакет хаба под `HUB_STORE_S3_PREFIX` (по умолчанию `<HUB_S3_PREFIX>store/`) |

Хранилище берёт настройки базы и бакета хаба. Своих настроек у него нет, пока их не задали:

| Переменная | По умолчанию | Что значит |
| --- | --- | --- |
| `HUB_STORE` | `on` | `off`: нет хранилища, возможности и маршрутов. Машины ведут себя по-старому |
| `HUB_STORE_DIR` | `<HUB_DATA_DIR>/store` | базы SQLite и, без S3, блобы |
| `HUB_STORE_DATABASE_URL` | база хаба | другая база для ревизий, `sqlite:///папка` или `postgres://…`. Postgres, указанный здесь, читается в раскладке центра design-sync (`ds_rooms`, `r_*`) |
| `HUB_STORE_S3_BUCKET` | `HUB_S3_BUCKET` | другой бакет того же S3 для блобов |
| `HUB_STORE_S3_PREFIX` | `<HUB_S3_PREFIX>store/` | где в бакете лежат блобы. Блоб — `<префикс>rooms/<комната>/blobs/<sha[:2]>/<sha>` |
| `HUB_STORE_LEGACY_SPACE` | не задана | slug пространства, чья библиотека — сама комната `design`, которую вёл центр design-sync |
| `HUB_STORE_PROFILE_ROOMS` | не задана | `<id пользователя>=profile-sergey,<id пользователя>=profile-rsk`: комнаты, в которых центр design-sync держал профили Claude, привязанные к id пользователя (не к почте: её учётка может лишь заявлять); машины человека синкают их вместо `profile-<id пользователя>`. Подробнее — «The Claude profile» в `docs/hub/store.md` |

`hub check-config` показывает, где лежит хранилище.

## Существующий центр design-sync

Хаб открывает базу и бакет центра design-sync как есть, не перекладывая файлы. Укажите его Postgres в
`HUB_STORE_DATABASE_URL`, его блобы — в `HUB_STORE_S3_BUCKET` и `HUB_STORE_S3_PREFIX`, а пространство, чья это была
библиотека, — в `HUB_STORE_LEGACY_SPACE`. Центр продолжает работать рядом с хабом, аренды его комнат общие. Токены и
участники центра не читаются: машина входит в хранилище своим ключом хаба.

## Бэкап, сборка мусора, перенос

```sh
hub store backup --dir /backup/store        # копия, с которой может стартовать хаб (или migrate); блобы копируются по хэшу
hub store gc --keep 20 --days 30 --dry-run  # посчитать, какие старые ревизии и ненужные блобы уйдут
hub store gc --keep 20 --days 30            # и удалить их (блоб живёт ещё сутки после того, как на него перестали ссылаться)
hub store migrate --from /path/to/store --rooms design --into-room design-<id пространства>
```

`backup` снимает согласованный снимок баз SQLite, пока хаб продолжает писать, а потом копирует блобы. С Postgres
базу бэкапят так же, как базу хаба ([миграции](../../hub/migrations.md)), а бакет — средствами самого бакета.

`migrate` копирует другое хранилище в хранилище этого хаба — то, что рантайм держал внутри себя
(`<каталог данных>/store`), или хранилище другого хаба. Копирует ревизию за ревизией, блобы по хэшу, и проверяет
копию. `--from-db` и `--from-dir` задают источник, у которого база и файлы лежат отдельно. Повторный запуск копирует
только новое.
